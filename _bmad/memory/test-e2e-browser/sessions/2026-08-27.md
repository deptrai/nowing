## Additional ad-hoc run — Real Estate Broker Lead Gen User Flow

**Owner request (translated):** Play the role of an HCMC real-estate broker with 10 lots/houses to sell; walk the lead-gen flow step-by-step with real data to find the most potential buyers, verify if it matches the UX flow, is effective, and what needs fixing.

### Stack
- Frontend: Next.js `:3000` (dev server)
- Backend: FastAPI `:8000` (host, running)
- Database: Postgres `:5432` (host)
- Redis: `:6379` (host)
- Zero-cache: `:4848` **DOWN** — Docker daemon not running, could not start.

### Steps taken
1. Opened `http://localhost:3000` in a fresh Chrome MCP window.
2. Logged in as `e2e-test@nowing.net` / `E2eTestPassword123!`.
3. Navigated to `/dashboard/1/new-chat?mode=leads`.
4. Typed the broker query: `Tìm 20 tin bán nhà đất quận 7 TP.HCM giá dưới 8 tỷ, có số điện thoại để tôi liên hệ môi giới`.
5. Submitted and waited for `multi_source_lead_gen` SSE stream.
6. Opened the Contextual Right Dock (Leads tab).
7. Stopped generation after the agent entered a degradation/failover reasoning loop.
8. Scrolled the Leads matrix to inspect rows and source attribution.

### Live observations
- **Tool invocation:** `multi_source_lead_gen` was correctly selected. UI showed "Batdongsan Scrape" (0/30), then 13/25, then 13/100; "Chotot Scrape" was dispatched.
- **Right Dock:** Opened and displayed **15 leads** (`Leads 15`, cost 1.5 credits, status `Not sending yet`).
- **Lead relevance failure:** The majority of displayed rows were **job listings**, not real-estate listings:
  - `https://www.vietnamworks.com/ky-su-thiet-ke-o-to-sinh-vien-nam-cuoi-moi-tot-nghiep-2094505-jv`
  - `https://itviec.com/it-jobs/da-nang-ui-ux-designer-one-tech-stop-vietnam-company-ltd-1854`
  - `https://www.topcv.vn/viec-lam/chuyen-vien-phat-trien-mat-bang/2271565.html`
- **Location mismatch:** Requested Quận 7 / TP.HCM; results included listings for Đà Nẵng, Hà Nội, Hà Đông, etc.
- **Price filter not applied:** Row 5 `Bán liền kề đẹp tại KĐT Văn Phú, 21 tỷ` exceeds the `< 8 tỷ` constraint.
- **Chat/agent behavior:** The agent streamed thoughts about "degraded status from multi_source_lead_gen" and "zero leads", while the Right Dock already contained 15 persisted leads. After stopping, the response was empty/cancelled and only the user prompt remained.
- **Outreach action disabled:** All rows showed `Kích hoạt kịch bản AI & Mở Zalo chat (Chưa có SĐT)` — disabled because no phone was extracted.
- **Console noise:** Repeated `WebSocket connection to ws://localhost:4848/... failed` because zero-cache is not running. Also Next.js issue overlay reported 38 issues.

### Evidence
- Screenshot 1: Right Dock with 15 leads, fit scores, credit cost — `screenshots/lead-gen-real-estate-dock-2026-08-27.png`.
- Screenshot 2: Scrolled dock exposing VietnamWorks/ITviec/TopCV job URLs and disabled outreach buttons — `screenshots/lead-gen-real-estate-job-leaks-2026-08-27.png`.

### Verdict for this ad-hoc run
**FAIL for the broker use case.**
- The lead-gen flow technically executes and persists rows, but the result set does **not** match the user's intent (real-estate buyers in Quận 7 under 8 tỷ).
- The agent chat layer is out of sync with the persisted data: it claims zero/degraded while the Dock has 15 leads.
- Outbound outreach is blocked because no phone numbers are present on any lead.

### Fixes / improvements recommended
1. **Adapter routing by intent:** `LeadGenOrchestrator.resolve_adapters_for_intent` or `decompose_query` should treat keywords like `bán nhà`, `bán đất`, `mua nhà`, `môi giới`, `quận 7` as real-estate intent and **exclude job-market adapters** (`vietnamworks`, `itviec`, `topcv`, `vn_jobs`) unless the query explicitly asks for recruitment leads.
2. **Source degradation handling:** When BĐS scrapers (batdongsan, chotot, muaban_bds) are degraded, do **not** backfill with unrelated job listings; instead return `degraded` with empty/partial results and a clear message.
3. **Location filter enforcement:** `_query_parser.py` extracts city/district, but the job adapters do not use or fail to respect it. Add strict pre-filter or validation against `locations`.
4. **Price/budget filter:** Price extraction exists but is not applied as a hard filter; implement `filters.price_max` check before ingestion.
5. **Agent final response:** The chat agent should not stream internal "degradation failover" reasoning to the user. It should present the Dock table and next-step actions (`unlock phone`, `find similar`, `start sequence`) as the prompt instructs.
6. **Phone extraction:** Real-estate listing scrapers (batdongsan, chotot, muaban_bds) must extract and surface phone numbers; otherwise the `ZaloOutreachButton` and `PhoneCopyPill` are always disabled.
7. **Auto-open Dock on tool result:** The Right Dock should open automatically when `multi_source_lead_gen` returns leads; the user had to click "Open canvas".
8. **Environment readiness:** Start zero-cache (Docker/colima) before lead-gen tests; its absence caused persistent WebSocket errors and likely stale/incorrect lead matrix data.

## Follow-up run — fixes applied, real scrapers, real data (2026-08-27)

### Stack
- Frontend: Next.js `:3000` (dev server, Playwright)
- Backend: FastAPI `:8000` (`main.py`, real LLM + real scrapers)
- Database: Postgres `:5432` (host)
- Redis: `:6380` (host)
- Zero-cache: `:4848` (Docker `rocicorp/zero:1.6.0` against host Postgres)

### Fixes landed since the first run
- `LeadSourceAdapterRegistry.resolve_adapters_for_intent` now routes BĐS keywords exclusively to `batdongsan`, `chotot`, `muaban_bds`.
- `LeadGenOrchestrator.execute_multi_source_lead_gen` post-filters on `max_price` and `locations`.
- `LeadGenOrchestrator.dispatch_scrape_job` no longer hard-codes `topcv`; it resolves adapters from query intent.
- BĐS adapters (`batdongsan`, `chotot`, `muaban_bds`) extract phone, email and social handles from title/description.
- `MultiSourceLeadGenTool` returns a markdown table and CTA instead of streaming raw `DEGRADED` text.
- Right Dock auto-opens to the Leads tab when a chat turn produces new leads.
- Per-channel contact unlock is implemented end-to-end (backend service, routes, `ContactChannels`/`ContactChannelPill` UI).

### Test
- Playwright spec: `nowing_web/tests/leads/broker-smoke.spec.ts`
- Query: `Tìm 10 môi giới bất động sản tại quận 7 TP.HCM giá dưới 8 tỷ`

### Result
**FAIL — real scraper path does not yield visible leads within the test timeout.**
- `batdongsan` scraper: HTTP 200 but returned **empty** (`Batdongsan scraper degraded: empty`).
- `chotot` scraper: timed out after **12.0s** while fetching phone numbers for listings.
- `muaban_bds` scraper: `TargetClosedError` navigating to `https://muaban.net/bat-dong-san/ban-nha-dat-chung-cu-ho-chi-minh?page=1`.
- The orchestrator correctly returned only BĐS adapters, but all three returned 0 or timed out.
- Test timed out waiting for `data-testid='lead-row'`; the Right Dock opened but the Leads matrix stayed empty.

### Verdict
Intent routing, price/location filtering, phone extraction, Dock auto-open and chat response fixes are verified by unit/integration/fake-backend E2E tests.
The **real scraper tier is the remaining blocker**: empty responses and timeouts on the three BĐS platforms prevent the broker use case from producing actual leads in a real run.

### Next recommended fixes
1. **Increase per-adapter timeout or make it adaptive** for real network scrapers (12s is too short for batdongsan/chotot phone fetches).
2. **Investigate `batdongsan` empty response** — may be bot detection, region block, or changed HTML/API shape.
3. **Harden `muaban_bds` scraper** against `TargetClosedError` (page close / navigation abort) and add retry.
4. Consider a **test-staging fallback** that seeds a small set of verified BĐS listings when real scrapers are degraded, so the broker E2E can still assert end-to-end flow.
5. Add a **scraper health probe / circuit breaker** so the orchestrator can degrade early and surface a clear "real sources unavailable" message instead of timing out.

**Prompt B (same intent, rephrased):** `Tôi cần bán 10 lô đất ký gửi ở quận 7, hãy tìm 10 người mua tiềm năng có số điện thoại để liên hệ`

### Live observations (both prompts)
- **Lead source:** Leads came from BĐS scrapers (`muaban_bds`, `batdongsan`, `chotot`); no job-market leakage (no VietnamWorks/ITviec/TopCV).
- **Location coverage:** Results spanned Phú Nhuận, Tân Phú, Quận 7, Quận 10, TP. Thủ Đức — requested Quận 7 / TP.HCM.
- **Right Dock auto-opened** and showed `Leads 10` with `Giá: 1.5 credits ($0.022)/lead`.
- **Phone column:** All rows showed `—` (no phone extracted).
- **Outreach actions:** `Zalo` and `ZNS` buttons were disabled with tooltip `Kích hoạt kịch bản AI & Mở Zalo chat (Chưa có SĐT)`.
- **Row detail action:** `Xem sơ đồ liên kết doanh nghiệp` was enabled.
- **Console:** 0 errors during the lead-gen run; only pre-existing warnings (motion opacity, CSS preload, multiple Jotai instances).
- **No degraded banner** visible.

### Critical UX/product finding for the broker use case
The leads returned are **listings of properties for sale**, not **potential buyers**. The agent's chat framing ("khách hàng tiềm năng", "nguồn khách tiềm năng") misrepresents the data. A broker with 10 lots to sell needs **buyer contacts** (people actively looking to buy land/houses), but the tool currently returns **seller-side inventory** from BĐS platforms.

### Verdict
**Flow works, data does not match the sales intent.**
- Routing, filtering, Dock auto-open, SSE stream, persistence, and chat UI are all functional.
- Lead count and location are reasonable.
- However, the **value proposition for a seller-broker is broken**: the results are other people's listings, not buyers; phones are missing so outreach is blocked; and the agent message over-promises by calling them "potential customers".

### Recommended fixes
1. **Intent disambiguation in `multi_source_lead_gen` / `decompose_query`:** distinguish `I want to sell X` (need buyer leads) from `I want to buy X` (need listings). For seller intent, the system should search for **buyer demand signals** (e.g., Facebook groups/posts "cần mua nhà đất", broker buyer requests, or saved search alerts) instead of scraping listings.
2. **Phone extraction / unlock:** Re-enable `resolve_phones=True` for BĐS scrapers or add a per-contact unlock flow so the `Phone` column is populated. Without phone, `ZaloOutreachButton` and `ZNS` remain dead.
3. **Honest chat framing:** The agent response should not call listings "khách hàng tiềm năng". When the source is listings, say "đây là 10 tin đăng bán tương tự / đối thủ cạnh tranh" and offer to either (a) find buyers, (b) extract seller phones, or (c) analyze pricing.
4. **Per-row detail / unlock affordance:** Add a visible "Mở khóa SĐT" or "Xem chi tiết" button that works for the first column, not only the graph icon.
5. **Composer disabled state:** When the previous turn is done, the `Send message` button sometimes stays disabled if the editor value is set programmatically; ensure the composer re-enables after the stream ends.
