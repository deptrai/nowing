# Blind Hunter Findings — Story 24.3 working tree diff

Reviewed the working-tree diff at `_bmad-output/implementation-artifacts/review-24-3-working-tree.diff` and traced the current source tree for the P0 surfaces called out in the story, the human-review gate, and the NFR/test reviews. Findings below are descriptions only, with exact file paths and line numbers.

- `nowing_backend/app/services/workspace_credit_service.py:163-183` and `:191-215`: `deduct_credits` decrements `Workspace.credit_micros_balance` before it attempts the `WorkspaceMembership.monthly_spent_micros` cap-gated `UPDATE ... WHERE`. If the second update fails (concurrent spend, cap lowered, or race), the balance has already been reduced and is never refunded, so shared workspace credits are consumed even though the spend cap blocked the member-side charge.

- `nowing_backend/app/services/workspace_credit_service.py:330-339`: `record_spend` returns a no-op success with `member_monthly_spend_cap: None` whenever the user has no `WorkspaceMembership`. Any caller that reaches this code with a non-member `user_id` (service account, API key, or mis-routed owner ID) silently bypasses per-seat spend-cap enforcement.

- `nowing_backend/app/services/workspace_credit_service.py:449-489`: `refund_credits` credits `Workspace.credit_micros_balance` before it decrements `WorkspaceMembership.monthly_spent_micros`. If the membership update fails or the row is gone, the shared pool is inflated while the member's spent counter stays high, permanently distorting the per-seat cap.

- `nowing_backend/app/services/workspace_credit_service.py:141-146` and `:322-328`: `deduct_credits` and `record_spend` branch into `_deduct_credits_fake` and `_record_spend_fake` whenever `hasattr(session, "workspaces") and hasattr(session, "memberships")`. That is a test-only seam that can be triggered by any session carrying those attributes, and it means the unit tests do not exercise the production `UPDATE ... WHERE ... RETURNING` SQL that enforces INV-24.4.

- `nowing_backend/app/services/billing_event_service.py:818-833`: `_record_business_event` calls `record_spend` outside the `try` block that refunds `monthly_spent_micros` on `wallet_credit.apply_debit` failure, and it never converts `SpendCapExceededError` to `wallet_credit.InsufficientCreditsError`. Callers such as `contact_unlock_service.py` catch `InsufficientCreditsError` but not `SpendCapExceededError`, so a spend-cap hit returns a 500 instead of a controlled credit error.

- `nowing_backend/app/capabilities/core/billing.py:36-71`: `_debit_with_workspace_spend_cap` converts `SpendCapExceededError` correctly, but it calls `wallet_credit.apply_debit` with no surrounding `try/except` and never invokes `refund_member_spend` when `apply_debit` fails. If the user wallet is insufficient after `record_spend` succeeds, the member's `monthly_spent_micros` is incremented and leaked until a manual refund.

- `nowing_backend/app/services/lead_assignment_service.py:208-216`: `assign_leads_batch` calls `get_eligible_members` once per lead in a loop, and the capacity `func.count(Lead.id)` query cannot see the unflushed `LeadAssignment` rows that `assign_lead` just added. Multiple leads in the same batch can be assigned to the same member beyond `lead_capacity`.

- `nowing_backend/app/services/lead_assignment_service.py:130-188` and `:225-315`: `assign_lead` and `reassign_lead` always insert a new `LeadAssignment` row with `status="assigned"` but never update or inactivate the prior assignment. This allows multiple active `LeadAssignment` records for the same lead, bloating the table and making current-lead counts and audit history ambiguous.

- `nowing_backend/app/services/lead_assignment_service.py:152-160`: the round-robin cursor falls back to `self._in_memory_cursors` when Redis is not available. That state is local to each process, so multiple workers or containers will restart cursors independently, breaking round-robin fairness and increasing the chance of duplicate concurrent assignments.

- `nowing_backend/app/services/lead_assignment_service.py:236-280` and `nowing_backend/app/routes/lead_pipeline_routes.py:338-379`: `reassign_lead` checks the target member's lead count before it inserts, but the count is not atomically serialized with the insert. Two concurrent reassignments can both see `current_leads < max_capacity` and insert, exceeding `lead_capacity`.

- `nowing_backend/app/routes/lead_pipeline_routes.py:96-109, 165-247, 259-331, 334-427`: CRM routes only verify workspace membership through `check_workspace_access` and never enforce INV-23.6 role/assignment visibility. Any member can list any lead, view any timeline, transition any card, create activity logs on any lead, and invoke batch or manual reassignment.

- `nowing_backend/app/routes/lead_pipeline_routes.py:219-226`, `nowing_web/lib/apis/base-api.service.ts:271-279`, and `nowing_web/components/leads/pipeline/LeadKanbanBoard.tsx:415-433`: the 409 conflict response returns `current_version` and `current_stage_id` nested under `detail`; `base-api.service.ts` stores the entire JSON body in `AppError.data`; the Kanban board then reads `err.data.current_version`. Because `data` is `{"detail": {...}}`, `data.current_version` is undefined, so the client cannot merge the server state and will keep retrying with the stale version, producing a loop of 409s.

- `nowing_backend/alembic/versions/221_add_multi_seat_crm_and_credit_pooling.py:87-110`: the migration uses raw `text(f"ALTER TABLE {table_name} ...")` to add `stage_id`, `assigned_to_user_id`, and `version` to `leads` and `leads_partitioned`. It does not use `IF NOT EXISTS` for the foreign-key clause, and adding indexes to a potentially partitioned parent with `text` may not propagate to child partitions, risking migration failure or missing indexes on partitions.

- `nowing_backend/app/services/phone_waterfall_service.py:937`, `nowing_backend/app/services/outcome_pricing_service.py:180`, `nowing_backend/app/services/etl_credit_service.py:126`, `nowing_backend/app/gateway/zalo/zns_client.py:287`, `nowing_backend/app/services/web_crawl_credit_service.py:141`, and `nowing_backend/app/services/platform_scrape_credit_service.py:75`: these paths still debit the user wallet directly without routing through `WorkspaceCreditService.record_spend`. Billable workspace operations triggered through these call sites bypass the per-seat spend-cap gate and fail to update `monthly_spent_micros`.

- `nowing_backend/app/routes/lead_pipeline_routes.py:382-427`: `assign_leads_batch` is available to any workspace member and does not verify that the supplied `lead_ids` exist in the workspace or are unassigned before delegating to the service, conflating missing leads with "no eligible members" in the returned `unassigned_lead_ids`.

- `nowing_backend/app/services/workspace_credit_service.py:582-598`: `set_member_spend_cap` mutates the `WorkspaceMembership` object but does not flush or commit, and it accepts a cap below the current `monthly_spent_micros` without any overage handling. Reducing a cap below already-spent usage can strand a member with a negative effective allowance and no explicit audit of who made the change.

- `nowing_backend/app/proprietary/platforms/masothue/parsers.py:197` (present in the working-tree diff): the bounds check `city = parts[i + 1] if i + 0 < len(parts) else None` is a tautology (`i + 0` is always `< len(parts)` when `i` is in range) and can access `parts[i + 1]` out of bounds. This change is unrelated to Story 24.3 and suggests scope bleed in the working tree.

- `scripts/mutation-gate.py:329` (present in the working-tree diff): the `run_cosmic_ray` helper changed to `if step != "exec" and result.returncode != 0`, so a failing `cosmic-ray exec` step is silently ignored. This can produce a mutation gate that reports success even though the mutation suite did not actually run or failed.

- `_bmad-output/implementation-artifacts/review-24-3-working-tree.diff` itself: the diff is not story-scoped to 24.3. It appends review artifacts, adds a new `.agents/skills/bmad-agent-e2e-tester` skill, edits `scripts/mutation-gate.py`, and includes `masothue` parser/test changes. Mixing these unrelated changes makes the P0 surface harder to review and increases the risk of unreviewed side effects landing alongside the CRM/credit work.
