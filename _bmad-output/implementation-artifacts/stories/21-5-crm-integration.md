# Story 21.5: CRM Integration & Write-Back

## Story

As a sales operations manager,
I want lead intelligence data synced with our CRM,
So that reps work from a single source of truth.

## Acceptance Criteria

### AC-1 — CRM connection with OAuth 2.0
**Given** a workspace user wants to connect Salesforce, HubSpot, or Pipedrive,
**When** they initiate OAuth authorization,
**Then** the system creates a `CrmConnection` row with `status=pending`, generates a PKCE `auth_url` with `OAuthStateManager`, and redirects the user to the provider.

**And** the callback route validates the state, exchanges the code for `access_token` / `refresh_token`, fetches account metadata, and stores encrypted credentials in `CrmConnection.credentials_encrypted` using `TokenEncryption`, with `status=active` and `last_sync_at` set.

### AC-2 — Connection uses `CrmConnection` with `client_id` and `workspace_id`
**Given** a `CrmConnection` row is persisted,
**When** it is queried or joined,
**Then** it always includes `id: UUID`, `workspace_id: Integer`, `client_id: CITEXT | None`, `provider` (`salesforce` | `hubspot` | `pipedrive`), `credentials_encrypted: str`, `sync_config: JSONB`, `last_sync_at: datetime | None`, and `created_at`.

**And** it inherits `Base + TimestampMixin` (not `BaseModel`), uses a UUID primary key, and has composite indexes on `(workspace_id, client_id, provider)` and `(workspace_id, provider, status)`.

### AC-3 — Phase 1: Read-only dedup (MVP default)
**Given** a `CrmConnection` is active and `sync_config.dedup_enabled = true`,
**When** a `Lead` is created or updated,
**Then** `CrmDedupService` matches `Lead.domain` and `VerifiedContact.email` against CRM contacts via provider API.

**And** it flags duplicates before they reach CRM and writes a `CrmSyncLog` row with `direction=nowing_to_crm`, `entity_type=lead`, `status=success`, and a `duplicate_detected` note.

### AC-4 — Phase 2: Write-back (gated by `sync_config.writeback_enabled`)
**Given** a `CrmConnection` is active and `sync_config.writeback_enabled = true`,
**When** a lead is verified and enriched,
**Then** `CrmWriteBackService` pushes `Lead`, `VerifiedContact` (name, title, email, phone with consent/legal basis), and `LeadScore` to CRM as a lead/contact record with configurable field mapping.

**And** the mapping is read from `sync_config.field_mapping` and supports `Lead` → `Contact` / `Lead` object depending on `provider`.

### AC-5 — Phase 3: Bidirectional sync (gated by `sync_config.bidirectional_enabled`)
**Given** a `CrmConnection` is active and `sync_config.bidirectional_enabled = true`,
**When** the CRM sends a webhook for contact/lead/deal updates,
**Then** the webhook receiver validates the signature, finds the matching `Lead` by `crm_record_id`, and updates the `Lead` fields (status, owner, deal stage) without overwriting Nowing-native computed fields (`fit_score`, `intent_score`, `composite_score`).

**And** a `CrmSyncLog` row is written with `direction=crm_to_nowing`, `entity_type`, and `status`.

### AC-6 — Conflict resolution
**Given** the same lead is updated in both Nowing and CRM,
**When** a sync runs and detects a conflict,
**Then** the system uses last-write-wins based on `CrmSyncLog.synced_at` / `Lead.updated_at` / `CrmConnection.last_sync_at` and writes a `CrmSyncLog` row with `status=conflict` and the resolution.

### AC-7 — Sync audit log
**Given** any sync operation,
**When** it completes,
**Then** a `CrmSyncLog` row is written with `id: UUID`, `workspace_id: Integer`, `client_id: CITEXT | None`, `connection_id: UUID` (FK `crm_connections.id`), `direction` (`nowing_to_crm` | `crm_to_nowing`), `entity_type` (`lead` | `contact` | `lead_score` | `signal_event` | `enrichment` | `sequence_event` | `outcome`), `entity_id: UUID`, `status` (`success` | `conflict` | `error`), `error_message: str | None`, and `synced_at`.

### AC-8 — No billing event for sync
**Given** a CRM sync runs,
**When** it completes,
**Then** it does **not** write a `BillingEvent` for the sync itself. The only cost events are those already generated by upstream stories (21.1 signal scan, 21.2 lead scoring, 21.3 contact enrichment).

### AC-9 — RBAC and REST routes
**Given** a user with the correct permission,
**When** they call the CRM endpoints,
**Then** the following endpoints are guarded by `check_permission` with `Permission.CRM_CONNECT`, `CRM_READ`, `CRM_WRITE`, `CRM_DISCONNECT`, or `CRM_SYNC`:
  - `POST /workspaces/{workspace_id}/crm/{provider}/connect` — start OAuth (return `auth_url`).
  - `GET /auth/crm/{provider}/callback` — OAuth callback.
  - `GET /workspaces/{workspace_id}/crm/connections` — list connections.
  - `GET /workspaces/{workspace_id}/crm/connections/{connection_id}` — get connection.
  - `DELETE /workspaces/{workspace_id}/crm/connections/{connection_id}` — disconnect.
  - `POST /workspaces/{workspace_id}/crm/connections/{connection_id}/sync` — trigger sync.
  - `POST /workspaces/{workspace_id}/crm/connections/{connection_id}/dedup` — read-only dedup.
  - `GET /workspaces/{workspace_id}/crm/connections/{connection_id}/sync-logs` — list sync logs.

### AC-10 — Memory provenance and PII redaction
**Given** the CRM dedup or write-back produces a context document,
**When** it is persisted,
**Then** it writes a `Memory` row with `type=semantic`, `source_type=MemorySourceType.CRM_CONNECTION` or `CRM_SYNC`, `source_uuid=CrmConnection.id` or `CrmSyncLog.id`, `source_entity_type="crm_connection"` or `"crm_sync"`, and tags `["crm_context"]`.

**And** `redact_pii(..., context="lead_enrichment")` runs on `Memory.content`, `Chunk[]`, audit logs, and UI surfaces. `VerifiedContact` raw values remain in the PII vault (Story 21.3) and are never redacted.

### AC-11 — MCP tools
**Given** CRM is enabled for a workspace,
**When** an MCP client calls,
**Then** the following tools are available:
  - `nowing_connect_crm(provider)` — returns auth URL.
  - `nowing_list_crm_connections()` — list active connections.
  - `nowing_sync_crm(connection_id)` — trigger a sync.
  - `nowing_list_crm_sync_logs(connection_id)` — list recent sync logs.

**And** they are added to `MCP_TOOL_CATALOG` (group `LEAD_INTELLIGENCE`) and `EXPECTED_TOOLS` in `selfcheck.py`.

### AC-12 — Degradation and error handling
**Given** the CRM API fails, OAuth token is invalid, or the provider is not configured,
**When** a sync is attempted,
**Then** the service returns `degraded=true` with `degradation_reasons` (`provider_not_configured`, `token_expired`, `api_error`, `crm_not_found`) and writes a `CrmSyncLog` row with `status=error` and `error_message`.

## Dev Notes

### Architecture Patterns & Constraints

- **AD-31:** Every Epic 21 table must include `workspace_id: Integer` and `client_id: CITEXT | None` with indexes. `client_id` is the natural key of `vertical_clients.client_id`, not the UUID `id`.
- **AD-40:** CRM integration uses a read-first pattern. Phase 1 (dedup) is enabled by default. Phase 2 (write-back) and Phase 3 (bidirectional) are gated by `sync_config.writeback_enabled` / `bidirectional_enabled`.
- **AD-3 / FR-7:** OAuth 2.0 flow reuses `OAuthStateManager`, `TokenEncryption`, and the existing redirect/callback pattern from `app/routes/mcp_oauth_route.py` and `app/routes/oauth_connector_base.py`. No new *auth* table is created; credentials are stored encrypted in `CrmConnection.credentials_encrypted`.
- **AD-42:** CRM sync itself is not a billable business event. Do not write `BillingEvent` for sync. Upstream 21.1/21.2/21.3 already bill their own events.
- **AD-25 / AD-49:** `redact_pii(..., context='lead_enrichment')` runs on `Memory.content`, logs, and UI. `VerifiedContact` is the PII vault and is never redacted.
- **AD-44 / AD-47:** For Epic 21 UUID entities, `Memory.source_uuid` + `Memory.source_entity_type` is the authoritative provenance.
- **AD-45:** Existing `client_id: Text` columns must be migrated to `CITEXT` before Epic 21 tables are enabled if not already done. This is a pre-condition for the Epic.

### Data Model

```python
class CrmConnection(Base, TimestampMixin):
    id: UUID
    workspace_id: Integer
    client_id: CITEXT | None
    provider: str                # salesforce / hubspot / pipedrive
    status: str                  # pending / active / expired / disconnected
    credentials_encrypted: str   # encrypted JSON of OAuth tokens
    sync_config: JSONB
    last_sync_at: datetime | None

class CrmSyncLog(Base, TimestampMixin):
    id: UUID
    workspace_id: Integer
    client_id: CITEXT | None
    connection_id: UUID
    direction: str               # nowing_to_crm / crm_to_nowing
    entity_type: str             # lead / contact / lead_score / signal_event / enrichment / sequence_event / outcome
    entity_id: UUID
    status: str                  # success / conflict / error
    error_message: str | None
    synced_at: datetime
```

### Encryption Pattern

```python
from app.config import config
from app.utils.oauth_security import TokenEncryption

_enc = TokenEncryption(config.SECRET_KEY)

# Before write
crm_connection.credentials_encrypted = _enc.encrypt_token(json.dumps(credentials))

# After read
credentials = json.loads(_enc.decrypt_token(crm_connection.credentials_encrypted))
```

### OAuth Flow

```
1. User clicks "Connect Salesforce" in UI
2. POST /workspaces/{id}/crm/salesforce/connect
3. Backend creates CrmConnection(status=pending), generates PKCE + state
4. Redirect user to Salesforce auth URL
5. Salesforce redirects to /auth/crm/salesforce/callback?code=...&state=...
6. Backend validates state, exchanges code, fetches account info
7. Encrypt tokens, update CrmConnection(status=active)
8. Return success to frontend
```

### Dedup Flow (Phase 1)

```
1. Lead created or enrich completed
2. If dedup_enabled, fetch CRM contacts by domain/email
3. Compare with Lead/VerifiedContact
4. Flag duplicate -> CrmSyncLog(status=success, note=duplicate_detected)
5. If not duplicate and writeback_enabled, proceed to write-back
```

### Write-Back Flow (Phase 2)

```
1. Read Lead + latest VerifiedContact + LeadScore
2. Apply field_mapping
3. Push to CRM provider
4. Store crm_record_id in Lead (or CrmSyncLog) if available
5. Write CrmSyncLog(direction=nowing_to_crm)
6. Write redacted Memory summary
```

### Inbound Flow (Phase 3)

```
1. CRM webhook POST /webhooks/crm/{provider}
2. Verify signature
3. Find Lead by crm_record_id or email/domain
4. Apply mapped CRM fields to Lead
5. Never overwrite fit/intent/composite scores
6. Write CrmSyncLog(direction=crm_to_nowing)
```

### Conflict Resolution

- Compare `Lead.updated_at` vs `CrmSyncLog.synced_at` for the latest inbound update.
- If `synced_at > updated_at`, apply CRM value.
- Else keep Nowing value.
- Write `CrmSyncLog(status=conflict, error_message=winner + diff summary)`.

### Error Handling & Degradation

- Missing OAuth config: `degraded=true`, `degradation_reasons=["provider_not_configured"]`.
- Token expired / refresh failed: `degraded=true`, `degradation_reasons=["token_expired"]`; set `CrmConnection.status=expired`.
- Provider API 5xx/timeout: `degraded=true`, `degradation_reasons=["api_error"]`; retry with backoff (max 3).
- Lead not found: `degraded=true`, `degradation_reasons=["crm_not_found"]`.
- All errors write `CrmSyncLog(status=error, error_message=...)`.

### Phasing

| Phase | Scope | Default | Gate |
|---|---|---|---|
| 1 | Read-only dedup | Enabled | `sync_config.dedup_enabled` |
| 2 | Write-back to CRM | Disabled | `sync_config.writeback_enabled` |
| 3 | Bidirectional sync | Disabled | `sync_config.bidirectional_enabled` |
