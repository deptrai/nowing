# Blind Hunter Review — Story 7.7 MCP Server Tool Expansion

## Findings

- **Report export markdown mode truncates binary base64 into an undecodable snippet.** In `nowing_mcp/mcp_server/features/reports/__init__.py`, `_render_binary_export()` (lines 139–155) calls `clip(encoded, 50000)` and `_render_text_export()` (lines 132–137) calls `clip(text, 20000)`. `clip()` in `nowing_mcp/mcp_server/core/rendering.py` (lines 67–72) appends a plain-text truncation marker such as `… [1234 more characters truncated]` to the payload. Because the marker is injected inside the base64 string inside the code block, the documented command `echo <payload> | base64 -d > report.<ext>` will fail on any report larger than the clip limit. JSON mode returns the full payload, but the default markdown path is effectively broken for non-trivial files.

- **`nowing_chat` silently drops every SSE event that is not `text-delta`, `data-turn-info`, or `error`.** In `nowing_mcp/mcp_server/features/chat/__init__.py`, `_consume_once()` (lines 148–179) only handles three `ev_type` values. Status, citation, tool-execution, deep-research progress, and other future event types are discarded, so the model never sees the full response context. The buffering design in `_ask_turn()` (lines 105–145) also has no idle/stall timeout beyond the 600s total set in `NowingClient.stream_sse()` (`nowing_mcp/mcp_server/core/client.py`, lines 130–179), so a backend that stalls mid-stream will keep the tool hanging until the global timeout expires.

- **`nowing_automation_run` sends a `workspace_id` body that the backend endpoint does not accept or validate.** In `nowing_mcp/mcp_server/features/automations/__init__.py`, `_run_automation()` (lines 108–128) POSTs `{"workspace_id": resolved_workspace_id}` to `/automations/{automation_id}/run`. The backend route in `nowing_backend/app/automations/api/run.py` (lines 13–28) only accepts `automation_id` and a service dependency; it has no body model. The resolved workspace is never cross-checked against the automation's actual workspace, so the `workspace` parameter is dead data that could become a spoofing risk the moment the backend starts trusting the body.

- **`nowing_automation_run` does not validate the run response before rendering it.** `_run_automation()` does `run = run or {}` (line 123), then `_render_run_started()` (lines 99–105) does `run_id = run.get("id")` and `status = run.get("status") or "pending"`. If the backend returns `None` or an empty body, the markdown output will read `Run started: **#None** ...`, which is a misleading success message. The JSON branch is equally unsafe, producing `{"run_id": null, "status": "pending"}`.

- **Memory `type` parameters are unvalidated strings, and `nowing_memory_list` can force a backend 500 for invalid values.** `MemoryType` in `nowing_mcp/mcp_server/features/memory/annotations.py` (lines 35–40) is just `Annotated[str, Field(...)]` with no enum or Literal. `nowing_memory_list()` in `nowing_mcp/mcp_server/features/memory/__init__.py` (lines 221–225) passes that string to `GET /workspaces/{id}/memories`. The backend `list_memories()` in `nowing_backend/app/services/memory/repository.py` (lines 473–494) calls `MemoryType(type)` without catching `ValueError`, and the route in `nowing_backend/app/routes/memories_routes.py` (lines 136–163) does not validate the query. A model passing an invalid `type` will hit a raw 500 instead of a clean tool-level error.

- **`RunService.launch` classifies `DispatchError` by substring, which is fragile and over-broad.** In `nowing_backend/app/automations/services/run.py` (lines 84–88), `if "not found" in message` maps to HTTP 404 and everything else maps to 400. Any future `DispatchError` that happens to contain the words "not found" for a different reason will become a 404, and genuine server-side dispatch failures are forced into 400. The unit tests in `nowing_backend/tests/unit/automations/services/test_run_service_launch.py` (lines 91–128) reinforce this by asserting on the exact string, so the mapping is locked to wording rather than error kind.

- **Scraper tools for chotot/muaban drift from the story API contract.** The story spec (section 6) lists `nowing_chotot_bds_scrape` / `nowing_muaban_bds_scrape` parameters as `city`, `listing_type`, `district_id`, `min_price`, `max_price`, `min_area`, `max_area`, `max_pages`, and `max_items`. The actual tools in `nowing_mcp/mcp_server/features/scrapers/platforms/chotot_bds.py` (lines 40–47) and `muaban_bds.py` (lines 38–45) also expose `property_type` and `district`, and `muaban_bds.py` line 33 makes `city` default to `"ho-chi-minh"` even though the spec calls it required. This makes the tool schemas wider than the documented contract and may cause confusion or unexpected backend rejection.

- **`nowing_workspace_memory_update` parameter name and the image-generation tool field limits mismatch the contract and the backend.** The story spec (section 6) lists `content` as the required parameter for `nowing_workspace_memory_update`, but `nowing_mcp/mcp_server/features/team_memory/__init__.py` (lines 58–71) uses `memory_md` (which the backend does expect). For `nowing_image_generate`, `nowing_mcp/mcp_server/features/image_generation/__init__.py` (lines 43–70) does not set `max_length` on `model`, `size`, `quality`, or `style`, while `nowing_backend/app/schemas/image_generation.py` `ImageGenerationCreate` enforces `model: max_length=200` and `size/quality/style: max_length=50`. These gaps mean tool-level validation and the API contract can diverge.

- **`NowingClient.stream_sse()` is typed `-> Any` despite being an async generator.** In `nowing_mcp/mcp_server/core/client.py` (lines 130–137), the return annotation is `Any`, and the method `yield`s `SseEvent` objects at line 174. The type should be `AsyncIterator[SseEvent]` or `AsyncGenerator[SseEvent, None]`. The sloppy typing hides the real consumer contract and defeats static analysis for every caller, including `_consume_once()` in the chat tool.

- **`nowing_chat` creates an empty thread and leaves it orphaned if the chat turn fails.** In `nowing_mcp/mcp_server/features/chat/__init__.py`, `nowing_chat()` (lines 80–102) calls `POST /threads` and only afterwards calls `_ask_turn()`. If `_ask_turn()` raises a `ToolError` (for example from an `error` SSE event or busy retry exhaustion), the newly created thread with no turns remains in the workspace. There is no rollback or cleanup path.

- **The MCP tool test files are not present in the supplied diff.** The story artifact (`_bmad-output/implementation-artifacts/7-7-mcp-server-tool-expansion.md`, lines 348–355) lists `nowing_mcp/tests/test_team_memory_tools.py`, `test_image_generation_tools.py`, `test_memory_slice2_tools.py`, `test_automation_report_tools.py`, and `test_chat_tool.py`. The diff file only contains `nowing_web/tests` and `nowing_backend/tests` hunks; the MCP tool tests are absent. This leaves the new feature modules unreviewable for unit-test coverage and makes the claimed "103 passed" invisible in this review artifact.

- **`nowing_chat` retry backoff is deterministic and risks thundering-herd contention.** In `nowing_mcp/mcp_server/features/chat/__init__.py`, `_ask_turn()` (lines 121–138) retries on `ThreadBusyError` with `asyncio.sleep(min(_BUSY_CAP_SECONDS, 0.5 * (2**attempt)))`. The sleep schedule is purely exponential with no jitter, so multiple callers hitting a busy thread will retry at the same cadence and can re-collide.
